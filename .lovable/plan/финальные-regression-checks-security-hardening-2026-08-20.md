# Финальные regression checks — Security Hardening

Три проверки после перехода функций на `SECURITY INVOKER`, затем итоговый прогон. Ничего не публикуем до вашего подтверждения.

Текущее состояние (проверено сейчас): `cron.job` — джоб `purge-rate-limit-hits`, расписание `17 * * * *`, `active = true`, `username = postgres`. `rate_limit_hits` пуста (0 строк) после QA-очистки, тестовых заявок `QA TEST` нет. Время сейчас 02:11 UTC — ближайший реальный запуск cron в 02:17 UTC.

## 1. Cron после перехода на SECURITY INVOKER

Сначала вставляю одну контрольную запись в `rate_limit_hits` с `created_at` возрастом ~30 часов (scope `qa-retention`, синтетический `ip_hmac`, не связанный ни с чьим IP) и одну свежую запись как контроль того, что чистка удаляет только просроченное.

Затем жду фактического запуска в 02:17 UTC (опрос в цикле, без `sleep` как единственной команды) и проверяю:

- `cron.job_run_details` для `jobid = 1`: есть запись с `start_time` после времени миграции и `status = 'succeeded'`;
- `username` джоба остался `postgres`;
- `purge_rate_limit_hits` реально сработала: возвращаемое значение видно в `job_run_details.return_message`, запись возрастом 30 часов удалена, свежая — на месте.

Если запуск завершится ошибкой (например, прав `postgres` на таблицу не хватает уже без `SECURITY DEFINER`) — фиксирую точный текст ошибки, не правлю права молча и возвращаюсь к вам с вариантами.

До получения этого результата формулировка остаётся: cron на новой модели прав не подтверждён.

## 2. Повторный parallel rate-limit test на пустом bucket

Bucket уже пуст, так что тест идёт на чистом счёте. Отправляю 8 одновременных `submit-lead` запросов с тестовыми данными (`QA TEST`, `request` помечен как тестовый).

Ожидаю и проверяю строго:

- ровно 5 ответов `200 {"ok": true}`;
- ровно 3 ответа `429 rate_limited` с `retry_after`;
- ровно 5 новых строк в `rate_limit_hits` scope `submit-lead`;
- ровно 5 новых заявок в `leads`.

Побочный эффект, о котором предупреждаю заранее: 5 разрешённых заявок уйдут в Telegram и на почту как тестовые уведомления. Строки `leads` и hits после теста удаляю; уведомления в мессенджере удалить нельзя.

Если распределение окажется не 5/3 — это баг сериализации, фиксирую и разбираю до финального PASS.

## 3. Least-privilege: нужен ли service_role SELECT на sequence

Проверяю по факту, а не по предположению: отзываю `SELECT` на `public.rate_limit_hits_id_seq`, оставляя `USAGE`, и повторяю один успешный `submit-lead` + один `track-event` (оба делают insert в таблицы с BIGSERIAL/идентификаторами).

- Если insert проходит — `SELECT` не нужен, оставляем только `USAGE`.
- Если insert падает с permission denied на sequence — возвращаю `SELECT` той же миграцией и фиксирую в отчёте, что `USAGE, SELECT` — минимум для этой конфигурации.

## Итоговый прогон

После трёх проверок собираю в одном ответе:

- production build (`bun run build`) и typecheck;
- security linter (Supabase linter) — список и трактовка findings;
- cron status: `status`, `start_time`, `username`, факт удаления просроченной записи;
- parallel boundary result: 5 allowed / 3 rate_limited / 5 hits;
- фактический ACL `public.rate_limit_hits_id_seq` после шага 3.

Все тестовые данные удаляю (`QA TEST` заявки, QA-события, QA hits), продовые не трогаю. Обновляю `docs/security-audit-report.md` результатами. Публикация — только после вашего отдельного подтверждения.

## Технические детали

- Вставка контрольных записей в `rate_limit_hits` и их удаление — через миграции (DML вне migration tool недоступен).
- Изменение прав на sequence — отдельная миграция; при откате вторая миграция возвращает `SELECT`.
- Ожидание cron — опрос `cron.job_run_details` в цикле до появления записи с `start_time > ` времени вставки контрольной записи.
- Правок в `src/` эти проверки не требуют; возможные изменения кода — только если тест выявит реальный баг.
